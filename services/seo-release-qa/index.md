# SEO release QA: check the change before it reaches every page

A developer is ready to release a new template. The staging site looks good. What you need now is someone to check what that change does to search: the content crawlers receive, the URLs they follow, and the signals that tell them what belongs in the index. I can review that release as a defined piece of work.

## When to bring me in

This is useful before a redesign, a CMS upgrade, a new navigation system, a consent banner change, or a move from one rendering approach to another. It also fits a team that has already had an SEO audit and wants an independent check that its developer's implementation meets the brief. There is a specific release to examine, a list of expected changes, and a decision somebody needs to make.

## Agree the test before the release

I start with the pages and behaviors the change could affect. A product template needs product examples, an unavailable product, a category, and a route that should not exist. A navigation change needs the destinations it is supposed to expose. A media move needs the image and document addresses as well as the pages that contain them. The scope says which templates and URL sets will be checked in full and where a sample is appropriate.
- **Content:** the important text, links, and images in the initial response and in the rendered page.
- **Search signals:** titles, canonicals, robots directives, structured data, and the production sitemap.
- **Routing:** expected destinations, redirect behavior, missing pages, and any retired URLs.
- **Dependencies:** content held behind consent, interaction, old hosting, or an account that is about to close.

## What you receive

The deliverable is a release note with the test date, the build or deployment examined, the affected URLs, and a clear result for each agreed check. Failed checks include the observed behavior, the expected behavior, and enough evidence for a developer to reproduce the problem. Items I could not verify are labeled with the access or information needed to finish them. A green result for one template is not silently applied to the rest of the site.

## Why I look beyond the browser

My [consent banner investigation](https://christopherabraham.com/case-studies/consent-banner/) concerned article content that a normal browser session could show while a nonconsenting crawl could not. In the [event platform case](https://christopherabraham.com/case-studies/event-app-links/), discovery depended on how the application exposed its links. Those are examples of the gap this review is designed to find: an interface can look finished while an important search behavior is still broken.

## After deployment

I repeat the agreed checks against the public site, since staging cannot show every production redirect, cache rule, or domain setting. The handover separates release acceptance from later search observations. A response can be verified today; recrawling, indexing, and traffic changes need their own dated followup. My guide to [proving an SEO fix worked](https://christopherabraham.com/guides/prove-seo-fixes/) explains that second part.

## Questions about a release review

### Can you review a site another developer built?

Yes. I can work from a staging address and the release brief. Repository access helps when a finding needs tracing to a template or component, and any proposed code change can go through your team's normal review.

### Does this replace a complete SEO audit?

The review answers whether the named release meets its agreed search requirements. A broader investigation of an unexplained traffic loss belongs in a separately scoped audit.
